# 하드모드 코인 정산 연결 안내

## 현재 상태

프론트의 정산 요청·상태 관리·결과 표시와 백엔드의 HTTP API·정산 로직을 구현했다.
실제 인증, 하드모드 게임 기록, MySQL 저장소는 아직 연결하지 않았다.
현재 게임은 일반 모드이므로 실제 플레이에서 코인을 지급하지 않는다.

## 보상 정책

- 하드모드 검증 점수만 보상 대상이다. 일반 게임은 제외한다.
- 초기 공식은 `min(floor(score / 50), 200)`이다. 실제 하드모드 통계로 조정한다.
- 지급량은 백엔드가 계산한다. 프론트의 점수·localStorage 잔액은 정산 근거로 쓰지 않는다.
- 0코인도 정산 완료로 기록하고 같은 게임은 다시 지급하지 않는다.

## API 계약

| 기능 | 요청 | 성공 응답의 data |
| --- | --- | --- |
| 현재 잔액 | `GET /api/credit/v11/balances/me` | `{ coin }` |
| 게임 보상 정산 | `POST /api/credit/v11/game-rewards` | `{ rewardId, gameId, earnedCoin, coinAfterReward }` |

정산 요청 본문은 `{ "gameId": "서버 게임 ID" }`만 받는다. 사용자·점수·모드·지급량은 서버가 확인한다.
최초 정산은 201, 기존 정산 반환은 200이다. `coinAfterReward`는 정산 당시 잔액이며 현재 잔액과 다를 수 있다.
응답은 camelCase와 팀 공통 성공·실패 형식을 따른다. 오류의 `timestamp`는 UTC ISO-8601이다.
일반 날짜 필드는 현재 없다. 팀 날짜 규약의 두 형식은 날짜 필드 추가 전에 확정해야 한다.

## 프론트 파일별 역할

| 파일 | 책임 |
| --- | --- |
| `src/api/credit.ts` | 잔액·정산 요청, 응답 검증, 시간 초과와 오류 해석 |
| `src/features/gameReward.ts` | 게임별 정산 상태, 동시 요청 공유, 성공 결과 재사용, 수동 재시도 |
| `src/hooks/useGameReward.ts` | 정산 상태 구독·최초 요청·수동 재시도 제공 |
| `src/components/CoinReward.tsx` | 확인된 지급량의 아이콘·숫자만 표시 |
| `src/components/GameRewardStatus.tsx` | 정산 성공 시 `CoinReward` 표시, 나머지 상태는 비표시 |
| `PlayScreen.tsx` | 선택적인 `rewardSession`을 코인 표시로 연결 |
| `GameOver.tsx` | `rewardContent` 슬롯 표시, 정산 코드와 독립 |

## 나중에 연결할 순서

1. Identity 담당자의 인증된 전송 함수와 사용자 컨텍스트를 연결한다.
2. 서버 게임 시작 응답에서 사용자에 귀속된 `gameId`를 받는다.
3. 하드모드 종료 결과의 서버 저장·검증 완료를 확인한다.
4. `createCreditApi`에 서버 주소와 인증된 `fetcher`를 전달한다.
5. 게임별로 `createGameRewardSession({ gameId, mode: "hard" }, api.claimGameReward)`을 생성하고 `PlayScreen.rewardSession`에 전달한다.
6. 계정 변경·새 게임 시작 시 새 세션을 만든다. 로컬 생성 ID나 이전 게임 세션은 재사용하지 않는다.

## 원하는 화면에 코인만 표시하기

게임 오버 화면과 무관하게 아래 컴포넌트를 원하는 위치에 넣는다.
정산 성공 시 아이콘과 `+숫자`만 표시하며 확인 문구·카드·버튼은 포함하지 않는다.

```tsx
<GameRewardStatus
  session={rewardSession}
  className="hard-mode-reward"
  iconSize={28}
  style={{ fontSize: 32, color: "gold" }}
/>
```

크기·색상은 `className` 또는 `style`로 지정하고, 위치는 부모 레이아웃으로 정한다.
아이콘 색상만 바꾸려면 호출 화면의 CSS에 `--coin-reward-icon-color`를 지정한다.
확인된 금액을 이미 가지고 있다면 `<CoinReward amount={earnedCoin} />`만 사용해도 된다.
금액 표시 컴포넌트는 직접 API를 호출하거나 지급량을 계산하지 않는다.

로딩·오류 안내와 재시도 버튼이 필요한 화면은 `useGameReward(session)`의 `state`와
`retry`를 사용해 자체 디자인으로 표시한다. 코인 전용 컴포넌트는 이러한 UI를 강제하지 않는다.
일반 모드·정산 대기·실패에는 코인을 표시하지 않으며 성공한 0코인은 `+0`으로 표시한다.
기존 일반 게임은 정산 세션이 연결되지 않았으므로 지급 요청을 하지 않는다.

프론트는 클라이언트 `X-User-Id`를 인증 근거로 보내지 않으며 잔액을 직접 더하지 않는다.
응답이 유실되면 같은 `gameId`로 결과를 다시 확인한다. 실제 중복 지급 방지는 서버 저장소의 책임이다.

## 오류 처리

| 상황 | 처리 |
| --- | --- |
| 401, 403 | 안내 후 재시도 중단. 재인증 후 새 세션 사용 |
| 게임 없음·일반 모드 | 보상 실패 안내, 재시도 중단 |
| 미종료·결과 미검증 | 수동으로 같은 게임 재확인 가능 |
| 네트워크·시간 초과·5xx | 수동 재확인 가능 |
| 잘못된 응답·다른 게임 ID·잘못된 코인 값 | 성공으로 표시하지 않음 |

`CREDIT_NETWORK_ERROR`, `CREDIT_REQUEST_TIMEOUT`, `CREDIT_INVALID_RESPONSE`는 프론트 내부 식별자다.
서버 API에는 보내지 않는다. 코인은 음수·소수·JavaScript 안전 정수 범위 초과를 허용하지 않는다.

## MySQL 연결 시 백엔드 담당자와 확인할 사항

- `CreditSettlementStore` 구현을 추가한다. 현재 Entity·Repository·DDL·MySQL 설정은 없다.
- 사용자·게임의 유일성 제약과 정산 기록·잔액 갱신의 트랜잭션을 보장한다.
- 같은 사용자의 다른 게임이 동시에 정산돼도 잔액 갱신이 유실되지 않아야 한다.
- 장애·재시작·여러 기기의 재요청에도 기존 정산을 반환한다.
- 게임 기록·잔액이 다른 서비스 소유라면 해당 API와 복구 전략을 사용한다.
- `src/test`의 메모리 저장소는 테스트용이다. MySQL 트랜잭션 검증을 대체하지 않는다.

백엔드 Controller는 등록돼 있지만 실제 서비스·인증 공급자 Bean은 미등록이다.
MVC까지 도달한 미연결 요청은 503이며 기존 Security 필터는 계속 미인증 접근을 차단한다.
Security 필터의 공통 401/403 JSON 응답은 인증 담당자와 연결해야 한다.

## 작업 기록 — 2026-10-23

- 상점 화면을 카드·모달·조회 훅으로 분리하고 예시 상품과 테마 표시 정보를 별도 파일로 이동했다.
- 코인 API의 응답 검증·오류 처리와 보상 상태 전이를 이름 있는 함수로 분리했다.
- 백엔드 공통 예외가 CREDIT에 의존하던 구조를 공통 오류 인터페이스로 정리했다.
- 긴 JSX·CSS·Java 코드의 포맷과 import를 정리했다. 기존 게임 로직·보상 공식·API 경로는 유지했다.
- 프론트 134개, 백엔드 49개 테스트 통과. TypeScript 검사·Vite 빌드·Java 21 Gradle 빌드 성공.
- 브라우저의 임시 API 응답으로 세션당 정산 요청 1회·보상 표시·503 수동 재시도·401 안내·모바일 가로 넘침을 확인했다. 실제 서버 지급 검증은 아니다.
- 실제 인증·게임 기록·MySQL 통합 검증은 후속 작업이다.
- 코드와 `src/test`는 커밋 대상이며 `tmp`, `dist`, `build`, `.gradle`의 도구·생성물은 제외한다.
- 이번 정리 작업에서는 커밋하지 않았다.

## 백엔드 재검증 — 2026-10-26

- Java 21에서 `gradlew.bat build --rerun-tasks --no-daemon --console=plain`으로 기존 결과를 재사용하지 않고 전체 빌드와 테스트를 실행했다.
- 총 49개 통과, 실패·오류·건너뜀 0개. 정책 7개, 게임 결과 검증 8개, 정산 서비스 13개, Controller 17개, OpenAPI·보안 3개, 기존 앱 컨텍스트 1개다.
- 50점 단위 버림·200코인 상한, 일반 모드 제외, 소유권·종료·검증 상태, 최초/반복 정산, 동시 요청, 0코인, 저장 실패 후 재시도와 금액 초과를 확인했다.
- HTTP 공통 응답과 잘못된 요청·권한·미연결 오류, OpenAPI 생성과 미인증 접근 차단도 통과했다.
- 기능 코드는 수정하지 않았다. 실제 MySQL·Identity·하드모드 서비스는 미연결이며, 동시성·롤백 검증은 테스트 전용 메모리 저장소 기준이다.
- 상세 결과는 백엔드 `polyo/build/reports/tests/test/index.html`에서 확인할 수 있다. 이번 검증에서 커밋은 수행하지 않았다.

## 코인 표시 분리 — 2026-10-26

- 하드모드의 결과 화면이 달라져도 재사용할 수 있도록 금액 표시·정산 상태·게임 오버 화면을 분리했다.
- `CoinReward`는 아이콘과 금액만 표시하며 음수·소수·안전 정수 범위 초과는 표시하지 않는다.
- `GameRewardStatus`는 성공한 정산만 표시하고 `useGameReward`가 상태와 재시도를 제공한다.
- `GameOver`는 정산 세션 대신 `rewardContent`를 받아 표시한다. 기존 `PlayScreen.rewardSession` 접점은 유지한다.
- 기존 성공 안내 문구·0코인 설명·흰 카드·공통 오류 안내는 코인 컴포넌트에서 제거했다. 상태별 안내는 호출 화면이 구성한다.
- 보상 공식·API 계약·중복 요청 처리·백엔드·DB·실제 인증 연결은 변경하지 않았다.
- 검증: 프론트 138개 테스트, TypeScript 검사와 Vite 빌드 통과. 브라우저에서 코인 전용 표시·크기·배지 스타일·대기/오류 비표시·재시도·0코인을 확인했다. 실제 API 요청과 페이지 오류는 0건이었다.
- 검증 중 테스트 정규식이 SVG의 `<path>`를 문단 `<p>`로 오인했다. 태그 경계를 구분하도록 수정했고 전체 테스트가 통과했다.
- 커밋은 수행하지 않았다. 미리보기 도구는 Git에서 제외된 `tmp`에만 두었다.

## 커밋 전 최종 검증 — 2026-10-26

- 인증 오류 응답이 빈 본문·HTML일 때 재시도가 허용되던 문제를 재현하고 수정했다. HTTP 401·403을 오류 코드보다 우선하여 재시도를 차단하며, 공통 코드가 없는 응답에는 인증·권한 오류 코드를 보완한다.
- 해당 회귀 테스트 4개를 추가했다. 프론트 전체 142개 테스트와 타입 검사·프로덕션 빌드가 통과했다.
- 백엔드는 전체 49개 테스트와 Java 21 Gradle 빌드가 통과했다. 기존 결과를 재사용하지 않고 다시 실행했다.
- 브라우저에서 코인 표시·화면별 스타일·대기/실패 비표시·재시도·0코인과 상점 정렬·모달·모바일·게임 복귀·저장 상태 보존을 확인했다. 페이지 오류는 없었다.
- 기능 소스·테스트·연결 안내 문서가 커밋 대상이다. 개발일지 PDF 등 `output` 산출물, `tmp` 도구와 미리보기, `dist`·`build` 생성물은 제외한다.
- 실제 인증·하드모드 기록·MySQL 연결 및 실제 DB의 동시성·트랜잭션 검증은 후속 작업이다.
